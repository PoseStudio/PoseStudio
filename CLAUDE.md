# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PoseStudio is an early-stage, open-source Qt6/C++ desktop application for 3D character creation, posing, and scene building. The codebase today is a main window shell, an asset manager side panel backed by SQLite, a Preferences dialog, a menu bar, and a Vulkan-backed 3D viewport (`src/viewport/`) that draws an infinite floor grid through a real orbit camera and renders lit, textured geometry — both Wavefront `.OBJ` models and **fully rigged, morphable character figures** imported from their native scene format (`.duf`/`.dsf`). The figure pipeline is now the largest part of the project: per-material-zone geometry + physically-based materials, baked character-shape morphs, a skeleton with GPU linear-blend skinning, joint-driven pose correctives, Catmull-Clark subdivision, and an interactive posing UI (click-a-joint + rotate gizmo, anatomical joint limits, pose save/load, undo/redo) — see the 3D Viewport section below. The viewport also offers a selectable shade-mode picker (twelve modes including a photoreal PBR mode), MSAA anti-aliasing, and image-based lighting (IBL) from an HDR environment — with an Environment properties tab for live control (the analytic key/fill/rim rig is retained for the non-photoreal shade modes). The animation/timeline systems and final-frame (production) rendering described in README.md are still roadmap — they don't exist in code yet.

## Build

Requires Qt 6 (developed against 6.11.1, MSVC 2022 64-bit), CMake 3.21+, and the **LunarG Vulkan SDK** (https://vulkan.lunarg.com — supplies the Vulkan headers, loader, validation layers, and the `glslc` shader compiler). `find_package(Vulkan REQUIRED)` aborts configuration with a clear message if the SDK is absent, so the viewport can't be built without it.

```
cmake -B build -DCMAKE_PREFIX_PATH="C:/Qt/6.11.1/msvc2022_64"
cmake --build build
```

If `CMAKE_PREFIX_PATH` isn't passed, `CMakeLists.txt` falls back to the hardcoded path `C:/Qt/6.11.1/msvc2022_64` — never commit a change to that fallback to point at your personal Qt install.

GLM (math), AMD's Vulkan Memory Allocator (VMA), tinyobjloader (the OBJ importer's parser), and stb_image (HDR environment loading) are pulled in header-only via CMake `FetchContent` at pinned tags/commits (see the "3D VIEWPORT DEPENDENCIES" block) — a fresh clone needs only Qt + the Vulkan SDK, nothing vendored. tinyobjloader, like VMA and stb_image, is a single-header lib whose implementation is compiled in exactly one TU (`import/obj/objimporter.cpp` via `#define TINYOBJLOADER_IMPLEMENTATION`; stb_image in `viewport/stb_impl.cpp` via `#define STB_IMAGE_IMPLEMENTATION`). They're *populated* (downloaded) but their own CMake isn't run; we consume their headers directly via `target_include_directories`. GLM's Vulkan-convention flags (`GLM_FORCE_RADIANS`, `GLM_FORCE_DEPTH_ZERO_TO_ONE`) are set once project-wide as `target_compile_definitions` — never per-file, or translation units disagree on matrix layout (a silent-corruption bug).

The **native figure importer** (`import/figure/`, see the 3D Viewport section) adds two more `FetchContent` deps under the same no-configure treatment: **nlohmann/json** (header-only JSON, kept out of Qt so the importer core stays Qt-free — `QJsonDocument` would drag Qt in) and **miniz** (to inflate gzip-compressed scene files). miniz isn't header-only — it ships C sources — so two accommodations exist: (1) `project()` enables the **C** language (`LANGUAGES C CXX`) — without it CMake silently classifies miniz's `.c` files as non-buildable `<None>` and they never link; miniz's split sources (`miniz.c`/`miniz_tinfl.c`/`miniz_tdef.c`/`miniz_zip.c`) are compiled directly into the target via `target_sources`; and (2) a tiny shim header `cmake/miniz-shim/miniz_export.h` (on the include path) satisfies miniz.h's `#include "miniz_export.h"` — that file is normally generated by miniz's CMake, which we skip; for a static in-binary build its export macros are no-ops.

The build links `Qt6::Widgets`, `Qt6::Gui`, `Qt6::Sql`, and `Vulkan::Vulkan` (the loader; `QVulkanInstance`/`QWindow` live in Qt6::Gui). No Qt Network/3D/Quick modules. `CMAKE_AUTOMOC`/`AUTOUIC`/`AUTORCC` are all on, so new `Q_OBJECT` classes, `.ui` files, and resources just need to be added to the `add_executable` source list / `resources.qrc` — no manual moc/rcc invocation.

Two post-build mirror steps copy on-disk content next to the executable on every build (both true mirrors — `rm -rf` then `copy_directory`, not overlays, so renamed/removed source files don't linger): (1) `resources/Maquettes/` (the built-in asset library, real on-disk content — not embedded via `resources.qrc`, since the Asset Manager browses libraries through `QDir`, not Qt's resource filesystem); and (2) the compiled SPIR-V shaders. Shaders are GLSL under `src/viewport/shaders/`, compiled to `*.spv` by `glslc` via a per-shader `add_custom_command` (gated through the `PoseStudioShaders` custom target that `PoseStudio` depends on), then mirrored to `<applicationDirPath>/shaders` where `VulkanRenderer` loads them at runtime. Add a new shader by dropping the `.vert`/`.frag` in that folder and appending its name to the `SHADER_SOURCES` list in `CMakeLists.txt`.

**Cross-platform posture**: PoseStudio is meant to be fully cross-platform (Windows, macOS, Linux). The stack is portable by construction — Qt6, C++17, CMake, SQLite, Vulkan — and the codebase carries no `#ifdef` platform branches; platform differences are absorbed by Qt (window/surface creation via `QVulkanInstance`/`QWindow`) and CMake rather than hand-written per-OS code. Accommodations already in place: writable data lives in `QStandardPaths::AppDataLocation` (an installed app's own directory is read-only on macOS/Linux — see the Database section); the Windows icon resource (`resources/PoseStudio.rc`) is added to the target only `if(WIN32)`; and because macOS runs Vulkan through **MoltenVK** (a Vulkan-on-Metal translation layer), `VulkanContext` enables the spec-mandated `VK_KHR_portability_subset` device extension whenever a device advertises it (a no-op on Windows/Linux). **Caveat:** only the Windows/MSVC build has been exercised so far — the macOS/Linux paths are correct by construction but unbuilt/unrun, and the one known runtime unknown on macOS is whether Qt's `QVulkanInstance` auto-adds the *instance*-level portability-enumeration extension (verify on real Apple hardware before claiming macOS support).

There is no test suite, linter, or CI configuration in this repo yet.

## Architecture

**Source layout**: `src/` is organized into one folder per subsystem — `core/` (non-visual services: database, preferences manager), `shell/` (app chrome: menu bar, splash/About overlay, Fusion theming), `assets/` (Asset Manager), `preferences/` (the Preferences dialog + every panel), and `viewport/` (the 3D engine, itself split into `rendering/` + `scene/` + `import/`). Only `main.cpp` and the cross-cutting `constants.h` sit at the `src/` root. Every subsystem folder is on the compiler include path (`target_include_directories` in `CMakeLists.txt`), so headers are included by bare name (`#include "database.h"`) regardless of which folder includes them — when you add a new `src/` subfolder, add it there too or its headers won't resolve.

**Startup sequence matters** (`src/main.cpp`): the SQLite database is opened and `PreferencesManager` is loaded *before* any widget is constructed, because widgets (e.g. `AssetManagerWidget`) read preferences/DB state during construction. If you add a new manager/cache that UI depends on, initialize it in this same early block, not lazily inside a widget.

**Database** (`src/core/database.{h,cpp}`): single named QSqlDatabase connection (`"db_conn"`) shared process-wide via `QSqlDatabase::database("db_conn")` rather than opened per-call. The SQLite file (`posestudio.db`) lives in the platform's per-user app-data dir (`QStandardPaths::AppDataLocation`, derived from the app name set in `main.cpp` *before* `initializeDatabase()` runs) — not next to the executable, whose directory is read-only for an installed app on macOS/Linux. Older builds stored it next to the `.exe`; `initializeDatabase()` performs a one-time *move*-migration of that legacy file into the new location on a Normal launch (copy-then-delete, so a later Factory Reset can't resurrect it), and FactoryReset also clears any lingering legacy file. Schema lives in `resources/database/initialize.sql`, embedded into the binary via `resources.qrc`, and is executed both on `DbInitMode::FactoryReset` (which also deletes the existing file first, and is reachable from the app via Preferences → Factory Reset) *and* on a genuine first launch (no `posestudio.db` file yet) — `initializeDatabase()` checks `QFile::exists(dbPath)` *before* FactoryReset can delete it, so a fresh install always gets the schema even via `DbInitMode::Normal`. There is still no formal migration system, but additive schema changes for existing databases (new columns/tables) are applied unconditionally at the end of `initializeDatabase()`, each guarded to be a no-op once already present (e.g. a `PRAGMA table_info` check before `ALTER TABLE ADD COLUMN`, or `CREATE TABLE/INDEX IF NOT EXISTS`) — add new ones here rather than only in `initialize.sql`, or pre-existing installs will silently fail at the first query touching the new column/table.

`AssetLibraries` has an `AssetLibraryIsBuiltIn` flag for the one library that ships with the app ("Maquettes", at `<applicationDirPath>/Maquettes`): `initializeDatabase()` re-syncs that row's path to the current install location on every launch (in case the app moved) and `mkpath`s the folder as a safety net. Built-in libraries always sort first (`ORDER BY AssetLibraryIsBuiltIn DESC`) and are excluded from the user-manageable list in Preferences → Assets, but still appear/behave like any other library in the Asset Manager tree.

`Favorites` (`FavoriteID`, `FavoritePath` unique, `FavoriteSortOrder`) is a flat list of favorited asset file paths — no folders, no nesting. `FavoriteSortOrder` holds the user's manual drag order from the Favorites pane (see Asset Manager section below); new favorites append after the current max.

**Preferences manager** (`src/core/preferencesmanager.{h,cpp}`): a process-wide singleton (`PreferencesManager::instance()`) that loads the entire `Preferences` SQLite table into a `QHash` once at startup. Reads never touch the DB; writes update the cache and persist immediately. It is explicitly not thread-safe — only call it from the Qt GUI thread.

**Asset manager** (`src/assets/assetmanagerwidget.{h,cpp}`, the largest file in the project): the side-panel widget that browses physical asset library folders (paths stored in `AssetLibraries`) alongside virtual, user-defined "Collections" (`AssetCollections`/`AssetCollectionItems`/`AssetCollectionFolders` tables) and a flat "Favorites" list (`Favorites` table). Collections can nest arbitrarily deep via `AssetCollections.AssetCollectionParentID` (`0` = top-level) — any collection, at any depth, can hold its own flat asset items and folder shortcuts alongside further sub-collections, mirroring filesystem folder semantics. Favorites, by contrast, is intentionally flat — no folders, no sub-favorites, just asset items. `contextForTreeItem()` walks a tree item's ancestor chain to classify it as `Library`/`Collection`/`SearchResults`/`Favorites` regardless of nesting depth; prefer it over checking a node's immediate parent when context-menu or grid logic needs to know which "world" an item belongs to. Tree root order is Search Results, Favorites, Collections, then physical libraries (built-in libraries first). Key pieces:
- `AssetFolderProxyModel` wraps the filesystem `QStandardItemModel`-backed tree to mark folders as direct/indirect "hits" (i.e. contain or descend into a folder containing matching assets) for search/filtering, with results debounced via a pending-index queue rather than recomputed synchronously.
- `AssetTreeDelegate` / `AssetGridDelegate` fully override Qt's default painting for the directory tree and the thumbnail grid respectively — don't expect standard `QStyledItemDelegate` behavior; geometry constants they rely on (icon size, margins, gaps) are centralized in `src/constants.h` so the two delegates' size hints can't drift apart.
- Breadcrumb rendering is cached per `displayFolder()` call (`m_breadcrumb*` members) and only re-laid-out, not recomputed, on label resize. Virtual sources (Collections, Favorites) instead show a plain title (`m_currentTitleText`); `displayFolder()` and `refreshTitleLabel()` both branch on the same "is this a virtual path" check (`COLLECTION_` prefix or `FAVORITES_ROOT`) — keep them in sync if a third virtual source is ever added.
- Physical folders and DB-backed virtual Collections/Favorites are all rendered into the same `QTreeView`/`dirModel`, distinguished by `searchResultsRootItem`/`favoritesRootItem`/`collectionsRootItem` root nodes — when adding tree behavior, check which subtree (filesystem vs. virtual) an index belongs to before assuming filesystem semantics (e.g. rename-on-disk) apply.
- `buildAssetHits()` resolves a flat list of asset paths into thumbnailed `AssetHit`s (shared by `parseCollectionAssets`/`parseFavorites`); it groups by folder internally for efficient thumbnail scanning but always re-emits in the caller's *input* order — both Favorites and Collections rely on this to preserve the user's manual drag order, so don't reintroduce a hash-ordered return here.
- Both Favorites and Collections are sortable grids backed by their own per-row order column (`Favorites.FavoriteSortOrder`, `AssetCollectionItems.AssetCollectionItemSortOrder`); `AssetManagerWidget::isSortableView()` (true when `m_currentFolderPath` is `FAVORITES_ROOT` or a `COLLECTION_*` id) is the single gate for both the drag-reorder handling and the "Sortable" info-bar label — check it rather than re-deriving the same `FAVORITES_ROOT`/`COLLECTION_` checks elsewhere. The drag-to-reorder itself (`beginGridDrag`/`endGridDrag`/`gridInsertIndex`/`updateGridDropIndicator`/`persistGridOrder` + the `MouseButtonPress/Move/Release` block in the grid viewport's `eventFilter`) is a **hand-rolled** drag, not Qt's `QListWidget` `InternalMove`: in `IconMode`, Qt's built-in internal-move free-positions the icon instead of reordering rows, and its `QDrag` runs through the OS drag loop. The manual version tracks raw mouse events, floats a translucent ghost `QLabel` plus a between-items drop-line indicator, leaves the grid untouched until release (moving items mid-drag would reflow the layout under the cursor), and auto-scrolls via a `QTimer` when the cursor sits in the top/bottom edge zone. `persistGridOrder()` branches on which view is current to write back to the right table/column. `AssetGridDelegate::paint` checks a `gridDragging` dynamic property on the grid to suppress the hover highlight while this is active.

**Styling**: dark theme enforced via `app.setStyle(new AppProxyStyle("Fusion"))` in `main.cpp`, never the native OS style. `AppProxyStyle` (`src/shell/appproxystyle.h`) must be constructed with `"Fusion"` explicitly — a bare `AppProxyStyle()` wraps the platform *default* style (e.g. `QWindows11Style` on Windows) instead, silently defeating the whole point of forcing Fusion. All app-level theming (style + global tooltip animation toggles) lives in this one spot in `main.cpp`'s "Branding & theming" block, not scattered into widget constructors. **Menu drop shadows:** an app-wide event filter (`MenuShadowFilter`, installed on `qApp` in that same block) sets `Qt::NoDropShadowWindowHint` on every `QMenu` at its `Polish` event (before the native window is created). This is because the menus' `border-radius` (in `_menumanager.qss`) makes each menu a *translucent* popup window, which Windows would give a heavy native drop shadow — the filter strips that shadow app-wide while keeping the rounded corners (menu-bar dropdowns, submenus, context menus, and the viewport shader menu alike). **Gotcha:** `NoDropShadowWindowHint` also flips the popup to an *opaque* window on Windows — the filter re-asserts `Qt::WA_TranslucentBackground` to bring back the see-through corners, but that still leaves a 2-3px opaque black speck at each sharp outer corner (the triangle outside the border-radius won't clear to transparent). So the filter *also* clips each menu to a rounded-rect **mask** (radius matched to the QSS `border-radius`, applied on the menu's `Resize`) to cut those specks away. All three together — no-shadow flag + translucent background + rounded mask — give rounded corners, cleanly transparent corners, and no shadow. Don't re-add a shadow via QSS (`box-shadow` isn't supported anyway); this is the single control point. Stylesheets are modular (`global.qss`, `_assetmanager.qss`, `_menumanager.qss`, `_preferences.qss`) and concatenated in `loadStylesheets()` (`src/main.cpp`) in a fixed cascade order — later files override earlier ones, so module-specific overrides belong in the `_*.qss` files, not `global.qss`. Some custom widgets (e.g. `AssetTreeView`) expose `Q_PROPERTY` values (like `separatorColor`) specifically so QSS can drive C++ painting logic. `QDialog`/`QMessageBox` are dark-themed globally too — but note Qt's QSS engine doesn't apply selectors (e.g. `a { color: ... }`) to rich-text `<a>` links inside a `QLabel`; those need the color set inline in the HTML string itself (see the "Add Asset Folder" hint label in `assetmanagerwidget.cpp` for the pattern). Also note: avoid declaring *any* `border` (even `border: none;`) on a `QListView`/`QListWidget` `::item` rule unless you actually want one — doing so flips Qt to full CSS box-model rendering of that item, which can visibly inflate the selection/hover rect beyond the item's actual layout cell (this is why `#AssetManagerTree::item` and `#AssetLibraryList::item` deliberately have no `border` line). `outline: none;` is fine on a container (`#AssetManagerTree`, `#AssetLibraryList`) to kill the dotted focus ring, but don't assume it's a no-op everywhere in the cascade.

**Destructive operations** (e.g. Preferences → Factory Reset, in `src/preferences/factoryresetpreferencespanel.cpp`): rather than trying to reconcile every widget's in-memory state (the asset tree, `PreferencesManager`'s cache, etc.) after wiping the database, the app just relaunches itself via `QProcess::startDetached(QApplication::applicationFilePath(), ...)` followed by `QApplication::quit()`. Follow this pattern for any future action that invalidates broad in-memory state rather than writing ad-hoc refresh logic for every affected widget. The reset itself is gated inline on the page (type "RESET" into a text field to enable the button) rather than behind a separate confirmation popup.

**Preferences dialog** (`src/preferences/preferencesdialog.{h,cpp}`, `src/preferences/preferencespanel.{h,cpp}`, `src/preferences/*preferencespanel.{h,cpp}`): a modal `QDialog` with a vertical tab list (left) driving a `QStackedWidget` (right). Each tab is a `PreferencesPanel` subclass living in its own file (`AssetsPreferencesPanel`, `FactoryResetPreferencesPanel`, etc.) so areas can be built out independently — adding a tab means adding a new subclass file and one `addPanel()` call in `PreferencesDialog`'s constructor, not touching the others. `PreferencesPanel` provides shared chrome (heading + top-aligned content layout) plus `addDescription()`/`addPlaceholder()` helpers for standardized body-copy styling — use these instead of hand-rolling a `QLabel` with inline font-size, or the panel won't match the others. `MenuManager::openPreferencesDialog(initialTab)` is the one entry point that opens the dialog (Edit → Preferences, and the Asset Manager's "Manage Asset Folders" context actions both route through it) and wires the `AssetsPreferencesPanel`'s `librariesChanged`/`navigateToLibraryRequested` signals back to the live `AssetManagerWidget` — `MenuManager::setAssetManagerWidget()` must be called (from `main.cpp`, after the Asset Manager tab exists) before that wiring can attach, so don't move `setupMenus()` to run after it without checking this dependency.

**3D viewport** (`src/viewport/`): a Vulkan renderer, hosted in a custom `QWindow` (not Qt's `QVulkanWindow` — we deliberately own the device/swapchain/render passes for the flexibility advanced rendering will need). The subsystem is split into a thin Qt-facing layer and a **Qt-free rendering core**, and that boundary is load-bearing — keep it:
- `ViewportWidget` (`viewportwidget.{h,cpp}`) is the *only* class the rest of the app sees. It's a plain `QWidget` that owns the process's `QVulkanInstance`, embeds the `VulkanWindow` via `QWidget::createWindowContainer()`, and degrades to an inline `QLabel` (rather than crashing the app) if `QVulkanInstance::create()` fails. `main.cpp` just news one up where the old viewport placeholder was. It also owns the teardown *ordering*: its destructor explicitly `delete`s the `createWindowContainer` wrapper (hence the `VulkanWindow` and all its Vulkan objects) **while the `QVulkanInstance` member is still alive**. Without that, the base `QWidget` destructor would free the window *after* the `QVulkanInstance` member is gone, and the renderer would call `vkDestroyDevice` on a device whose instance was already destroyed — a crash on close. Don't drop that explicit delete. **Overlay gotcha:** because the viewport is a *native* child window (`createWindowContainer`), it composites on top of ordinary sibling/overlay `QWidget`s — so anything that must paint over the viewport (the boot/About `SplashOverlay`, any future HUD) must be a **top-level window** (constructed with the `Qt::Window` type flag, then positioned over the parent in global coords), not a child overlay. Window *hints* alone (`FramelessWindowHint`, etc.) don't promote a parented widget to a window — `isWindow()` stays false and it remains hidden behind the viewport.
- `VulkanWindow` (`vulkanwindow.{h,cpp}`, a `QWindow` with `surfaceType == VulkanSurface`) is the Qt↔Vulkan bridge and the *only other* file in the subtree allowed to include Qt. It lazily builds the `VulkanContext` + `VulkanRenderer` on first `exposeEvent` (the platform surface must exist first), pumps one frame per `QEvent::UpdateRequest` (re-arming `requestUpdate()` each frame for continuous redraw), and routes mouse/wheel input to the camera. **Camera drags are gated on `m_activeDragButtons`** — buttons whose press was actually seen *in this window* — not on `QMouseEvent::buttons()`: a modal dialog (e.g. the Import file picker) closing over the native child window can otherwise leak a button-held move to us and snap the camera, so a move only orbits/pans if its button's drag began here. **Right-click** (on release) opens an object context menu (`showObjectContextMenu`): it builds a world-space picking ray via `Camera::screenPointToRay`, asks `VulkanRenderer::pickModel` for the nearest model whose AABB the ray hits (box-level picking — `Model::intersectRay` slab-tests its local bounds; the renderer/scene own the geometry, so the window only deals in rays + model indices), and on "Delete" calls `VulkanRenderer::deleteModel`, which `vkDeviceWaitIdle`s before freeing so an in-flight frame can't reference the model's buffers. The `QMenu` popup is a top-level window, so it composites above the native viewport (unlike a child overlay — see the SplashOverlay note). It releases its Vulkan objects both on `QEvent::PlatformSurface`/`SurfaceAboutToBeDestroyed` (so they're gone before Qt frees the surface they reference) and in its destructor as a fallback — `releaseVulkan()` is idempotent. **Header gotcha:** `QPlatformSurfaceEvent` is pulled from `<QtGui/qevent.h>`, *not* `<qpa/qplatformsurfaceevent.h>` — the binary Qt install ships no qpa headers, so the seemingly-canonical qpa include fails to compile here.
- Everything under `rendering/` and `scene/` is **pure Vulkan + std + GLM, no Qt includes** (it takes `std::string` paths and `std::vector<char>` SPIR-V blobs, not `QString`/`QByteArray`). This keeps the engine core reusable and testable. Don't reach for a `Q*` type here just because it's convenient — push that concern up into `VulkanWindow` (e.g. `importObj` takes a `QString` at the `VulkanWindow`/`ViewportWidget` layer but hands a `std::string` to the renderer).

Ownership/lifetime is layered by how often things change: `VulkanContext` (instance handle, physical+logical device, queues, VMA allocator) is created once and lives until the surface dies. `VulkanSwapchain` (swapchain images, the shared depth buffer, render pass, framebuffers) is the resolution-dependent layer — `recreate()` rebuilds it on resize/out-of-date but deliberately *keeps the render pass* (it depends only on formats + sample count, which don't change). **MSAA:** the viewport renders multisampled — `VulkanContext::sampleCount()` picks the best of {4×, 2×} the device supports for both colour and depth (else single-sample), chosen once at device creation; the swapchain builds a transient multisampled colour target + a multisampled depth target and a render pass whose subpass **resolves** the MSAA colour into the (single-sample) swapchain image (attachment order colour(0)/depth(1)/resolve(2); the resolve attachment + `pResolveAttachments` only exist when `samples>1`, so there's a clean single-sample fallback). Every `VulkanPipeline` reads `context.sampleCount()` for its `rasterizationSamples` (all pipelines share the one MSAA render pass, so they must match). The renderer's two clear values (colour, depth) are unchanged — the resolve attachment is `DONT_CARE`/not cleared. This is what anti-aliases the figure silhouette. `VulkanRenderer` owns the per-frame state (command buffers, sync) and the swapchain plus the renderables — the `Scene` (imported meshes) and the `Grid` — and drives `acquire → record → submit → present`. Resize is coalesced: `notifyResize()` just sets a pending extent + flag, and the actual rebuild happens at the next `drawFrame()` (on `VK_ERROR_OUT_OF_DATE_KHR`/suboptimal/the flag) after a `vkDeviceWaitIdle`. Sync follows the standard pattern with one subtlety — `imageAvailable` semaphores and `inFlight` fences are per *frame-in-flight* (`kMaxFramesInFlight`, in `vulkancommon.h`), but `renderFinished` semaphores are per *swapchain image* (a submit-signalled semaphore mustn't be reused until that image's present completes), so they're resized whenever the swapchain image count changes.

`VK_CHECK` (`vulkancommon.h`) throws `VulkanError` on any non-success `VkResult`; `VulkanWindow::initializeVulkan()` is the catch boundary. VMA is header-only and must be compiled in exactly one TU — `vma_impl.cpp` is that file (`#define VMA_IMPLEMENTATION`), bound to the statically-linked loader (`VMA_STATIC_VULKAN_FUNCTIONS 1`), which is why `VulkanContext` can call `vmaCreateAllocator` without supplying a function-pointer table.

`VulkanPipeline` wraps one `VkPipeline` + layout. The *shared* fixed-function state (dynamic viewport/scissor — so pipelines survive resizes untouched — triangle-list topology) lives in the class; the knobs that differ between pipelines are passed in a small `PipelineConfig` (push-constant size/stages, alpha-blend on/off, depth test/write on/off, cull mode, primitive topology + line width — `LINE_LIST` drives the posing skeleton overlay — plus optional vertex-input bindings/attributes and descriptor-set layouts). Add a field there only when a real use case needs it — don't expose all of Vulkan's pipeline state speculatively. The mesh path has two pipeline *variants* (opaque + transparent) sharing one shader/layout; with the grid, three passes are drawn in this order inside the render pass:
- **Mesh** (`scene/scene.{h,cpp}` + `mesh.vert/frag`): the lit, **skinned** pipeline for imported geometry (OBJ meshes *and* figure zones). Interleaved `Vertex` (pos/normal/uv + `uvec4 joints`/`vec4 weights` for skinning) vertex buffers, a per-frame camera/lighting UBO in descriptor **set 0** (binding 0, vert+frag — carries the view/viewProj matrices, camera position, the **3-point studio lighting rig** (key/fill/rim direction+colour, world-space and fixed relative to the subject so lighting stays consistent as the camera orbits; `Scene::record` sets them), an ambient term, the shade-mode param, and the **9 SH coefficients** of the lighting environment's diffuse irradiance (the diffuse half of IBL)), per-material textures in descriptor **set 1** (binding 0 = diffuse *sRGB*, binding 1 = detail normal/bump *linear*; each has a 1×1 fallback — white / flat-normal — so the shader always samples and one pipeline serves textured and untextured meshes), a per-**model** joint-matrix storage buffer in descriptor **set 2** (binding 0, vertex stage — the `skinMatrix = poseGlobal·inverseBind` per joint), the scene-wide **image-based-lighting maps** in descriptor **set 3** (binding 0 = prefiltered specular cubemap, binding 1 = BRDF LUT; fragment stage — see the IBL paragraph below), and a 96-byte push constant (`MeshPushConstants` = `mat4 model` + `vec4 baseColor` [`a` = opacity] + `vec4 material` [`x` = roughness, `y` = normalMode, `z` = metalness]). The vertex shader applies linear-blend skinning (weighted blend of the vertex's joint matrices) before the model + view-projection transforms; a **static** model (OBJ, or any figure at bind pose) binds a single identity joint and its vertices default to weight `(1,0,0,0)`, so the same path leaves them untransformed. Each `Model` owns its joint buffer + a runtime skeleton and recomputes the matrices in `computeSkinMatrices()` when `setBoneRotation()` poses a joint. The fragment computes `baseColor * diffuse` albedo, a roughness-driven Blinn-Phong + Fresnel specular, and optional normal perturbation from the detail map via a screen-space cotangent frame (no vertex tangents; mode 1 = tangent-space normal, mode 2 = bump — mode 2 wired but not fed yet). **Selectable shade modes (viewport "shader picker"):** `mesh.frag` is an **über-shader** that branches on `cam.params.x` — a per-frame uniform in the camera UBO (which also now carries `view`, for the view-space normals matcaps need) — so switching modes is a one-int UBO write with **no pipeline swap** and instant effect. The branch is coherent across a draw (uniform), so it's cheap. Twelve modes, in shader-index order: `0` Rendered (the skin/subsurface Blinn-Phong above, lit by the analytic 3-point rig), `1` **PBR** (**the default** — the photoreal, **image-based-lit** mode: Cook-Torrance GGX with split-sum IBL — diffuse from the environment's SH irradiance (set 0), specular from the prefiltered environment cubemap + BRDF LUT (set 3) — plus **one** analytic key light for a crisp highlight and a subsurface band for skin, ACES-tonemapped; the fill/rim analytic lights are dropped here because the environment supplies wrap + rim), `2`–`4` **Matcaps** (Studio/Skin/Metal — procedural material-sphere shading from the view-space normal, no texture), `5` Toon/Cel, `6` Clay (matte neutral form study), `7` Lighting-Only (shading on white), `8` Flat Shaded (geometric per-triangle normal via position derivatives), `9` Normals (RGB), `10` Albedo (unlit), `11` UV Checker. The mode is plumbed `ViewportWidget → VulkanWindow (remembers it across the lazy renderer build) → VulkanRenderer → Scene::setShadeMode` → the UBO. The **UI** floats in the viewport's top-right corner: because the viewport is a native child window, it lives in a *top-level* frameless window owned by `ViewportWidget` (same compositing rule as `SplashOverlay`), kept glued to the corner via `syncOverlayPosition()` on the widget's resize/move + an event filter on the top-level window; `ViewportWidget::shaderModeNames()` is the single source of truth whose order IS the shader's mode index. Output stays linear (the swapchain is `_SRGB` and does the gamma encode); the HDR modes (PBR/matcap) tonemap first. **The selector is a `QPushButton` that opens a real `QMenu`** (12 checkable actions in an exclusive `QActionGroup`), *not* a `QComboBox`. This is deliberate: it makes the dropdown look and behave **exactly** like the File/Edit/Help menus — colours, hover, spacing, and top-down drop — for free, because it *is* a `QMenu` and inherits the global `QMenu` QSS in `_menumanager.qss` (`#252627` surface, `#314D7A` rounded hover). A styled `QComboBox` popup was tried first and abandoned: setting any stylesheet on a `QComboBox` makes its popup render item states (`:hover`/`:selected`) inconsistently — the highlight paints as a faint native tint instead of the themed colour, no matter how `QAbstractItemView`/`::item` are styled — and its popup also repositions to align the current row with the field. The button itself is themed to match the menu-bar surface + hover (`#ShaderModeButton`), and triggering an action calls `setShadeMode(i)` and updates the button text. **No back-face culling** — imported winding is inconsistent, so the fragment flips the normal per `gl_FrontFacing` for two-sided lighting. Drawn in two passes over the same models: an **opaque** variant (depth test+write) first, then an **alpha-blended transparent** variant (depth test, write off) for see-through zones — `Scene::record` binds each variant in turn and `Model::record(cmd, layout, transparentPass)` filters meshes by `Mesh::isTransparent()` (opacity < 1).
- **Floor grid** (`scene/grid.{h,cpp}` + `grid.vert/frag`): an *infinite* ground grid. It is NOT line geometry — it draws one full-screen quad and the fragment shader reconstructs the world point on the `y=0` plane per pixel (ray/plane intersect of the unprojected near/far points), then draws anti-aliased lines via `fwidth` derivatives and fades them out with distance. It writes correct `gl_FragDepth` (so scene geometry occludes it) but is alpha-blended with depth-*write off* (a transparent overlay mustn't occlude things behind the mostly-invisible plane), which is why it's drawn last (after the opaque mesh layer). Its push constant is a single `viewProj` matrix, visible to both stages (vertex inverts it to unproject; fragment uses it for depth). All look tuning (line colour, cell size, major-line interval, fade distance) lives as named constants at the top of `grid.frag`; there are no colored axis lines yet.

**Mesh rendering & model import**: `Scene` (`scene/scene.{h,cpp}`) is the mesh analogue of `Grid` — it owns the mesh pipeline, the per-frame-in-flight camera UBOs + descriptor sets (set 0), the shared set-1 layout + a 1×1 white fallback texture, and the list of imported `Model`s, exposing `addModel()` and a `record(cmd, camera, frameIndex)` the renderer calls before the grid. A `Model` (`scene/mesh.{h,cpp}`) is one imported file: a set of `Mesh`es (one per material group) under a shared transform, and it owns the `VkDescriptorPool` its meshes' set-1 descriptors come from (sized to its mesh count). Each `Mesh` owns device-local vertex+index buffers, a base color, an optional `VulkanTexture`, and a set-1 descriptor pointing at that texture (or the scene's white fallback when untextured — so one pipeline/shader serves both: `albedo = baseColor * white = baseColor`). GPU buffers go through `VulkanBuffer` (`rendering/vulkanbuffer.{h,cpp}`); textures through `VulkanTexture` (`rendering/vulkanimage.{h,cpp}`, an `_SRGB` sampled image with a full mip chain). Load-time transfers live in `rendering/vulkancommands.{h,cpp}`, which offers two paths: `submitImmediate` (one self-contained transfer = one submit + fence wait) and **`ImmediateBatch`** (record many transfers into a single command buffer, then one submit + one fence wait). `Model`'s constructor builds **one `ImmediateBatch` for the whole model** — every mesh's vertex/index buffers and texture record into it (via the batch-taking overloads of `createDeviceLocalBuffer` / `VulkanTexture`), and it's submitted exactly once. That's the key import-perf decision: the old per-resource `submitImmediate` cost ~3 blocking GPU round-trips *per mesh*, which dominated import time on models with many material groups; batching collapses it to one round-trip per model. Trade-off: all staging buffers are retained (via `ImmediateBatch::retain`) until that single submit completes, so peak staging memory is the sum across the model's meshes rather than one-at-a-time. The 1×1 white fallback texture still uses the plain immediate path (a lone one-off upload).

**Image-based lighting** (`scene/environment.{h,cpp}`, `rendering/iblmaps.{h,cpp}`, `viewport/environmentsource.{h,cpp}`): the PBR/default shading is lit by an HDR *environment*, not a hand-tuned rig — this is what replaced 3-point lighting as the default. `environment.*` (Qt-free core) generates a neutral **procedural studio** environment and bakes three IBL products on the CPU (no offscreen GPU passes — the codebase has no compute/render-to-texture infra): **9 SH coefficients** for diffuse irradiance (Ramamoorthi form; fed via the set-0 UBO every frame and reconstructed per-normal in `mesh.frag`), a GGX-**prefiltered specular cubemap** (`prefilterSpecular`, mip = roughness), and the environment-**BRDF LUT** (`integrateBrdfLut`) — the standard split-sum decomposition, with SH standing in for an irradiance cubemap. The BRDF LUT is environment-independent (roughness/NdotV only), so it's integrated once and reused; only the SH + prefiltered cubemap re-bake when the environment changes. `IblMaps` uploads the cubemap (RGBA16F, cube view, CPU-generated mip chain) + LUT (RG16F) and owns the images/samplers behind descriptor **set 3**; `Scene` owns the set-3 layout/pool/set. The CPU bake and the GPU upload are split so the former can run off the render thread: `bakeEnvironment()` (core, Qt-free) does the heavy CPU work (normalize + SH + prefilter) into a `BakedEnvironment`, and `Scene::applyBakedEnvironment()` does the fast GPU upload + set-3 swap (after a `vkDeviceWaitIdle`, since it swaps maps the pipeline samples). The procedural default is baked synchronously in the `Scene` ctor so set 3 is valid before the first frame. Real `.hdr` panoramas replace the procedural default: `environmentsource.{h,cpp}` is the **codec boundary** (uses `stb_image`'s `stbi_loadf`) — kept in the Qt-facing layer so the render core stays image-codec-free, exactly like model-texture decoding — and decodes an equirectangular `.hdr` into an `EnvironmentImage`. `VulkanWindow` loads `<appDir>/environment.hdr` (explicit override) or the bundled default panorama (`<appDir>/hdri/Golden Gate Hills.hdr`); a missing/unreadable file just leaves the procedural default. **The bake runs off the UI thread:** `VulkanWindow::beginEnvironmentBake` decodes + `bakeEnvironment`s on a `QtConcurrent` worker (watched by a `QFutureWatcher`) and applies the result on the GUI thread, guarded by a per-request id so a slower earlier bake can't clobber a newer pick — so switching HDRIs (the ~hundreds-of-ms CPU prefilter) never freezes the app; the viewport keeps rendering the current environment until the new one lands. The CC0 panoramas in `resources/hdri/` are real on-disk content mirrored next to the exe like Maquettes/shaders (their own POST_BUILD mirror step). `stb_image` is fetched via `FetchContent` (pinned commit) and compiled in one TU (`stb_impl.cpp`), same as VMA/tinyobjloader. **Live controls:** the exposure/diffuse/specular/ambient-fill/key/rotation/tonemap dials are `LightingSettings` (`scene/lightingsettings.h`, a plain-POD contract), fed through the UBO (`params`/`params2`) and driven by the **Environment properties tab** (`src/properties/environmentpanel.*`, a right-docker panel) with no re-bake — only switching the HDRI re-bakes. The analytic lights still live in the UBO for the non-IBL modes: only **Rendered** (mode 0) uses the full key/fill/rim rig; the other analytic modes (Toon/Clay/Lighting-Only/Flat) use just the key + ambient, and PBR uses only the key.

**Import subsystem** (`viewport/import/`): model import is a self-contained, Qt-free subsystem (same "engine core = std + Vulkan + GLM, no Qt" rule as `rendering/`+`scene/`), structured so new formats slot in without touching the renderer, the dispatch, or existing importers. Its center is a **format-neutral IR** — `ModelData`/`MeshData` (`import/modeldata.h`) plus the shared `Vertex` layout (`import/vertex.h`, the geometry contract importers produce and `Scene` uploads) — that carries no format identity of its own. Each importer implements the `MeshImporter` interface (`import/meshimporter.h`: `displayName()` / `extensions()` / `load(path) → ModelData`, throwing on failure), lives in its own per-format folder (today just `import/obj/objimporter.{h,cpp}`, the single tinyobjloader TU — it triangulates, de-indexes unique `Vertex`es, generates smooth normals when the file lacks them, groups faces by material, and records `Kd` as base color), and is dispatched by file extension through `ImporterRegistry` (`import/importerregistry.{h,cpp}`). The registry is built from **one explicit list in its constructor** (`m_importers.push_back(std::make_unique<ObjImporter>())`, mirroring the `SHADER_SOURCES` list in CMake). So **adding a format is: implement `MeshImporter` under a new `import/<fmt>/`, add one `push_back` to the registry, and add the files + the `src/viewport/import/<fmt>` include dir to `CMakeLists.txt`** — nothing else changes. A mesh's texture is expressed as a `TextureSource` — *either* a resolved external file path (OBJ's `map_Kd`) *or* embedded encoded image bytes (e.g. a texture packed into a `.glb`) — so the IR already spans external and embedded sources; importers never decode.

Image decoding is deliberately **not** in the Qt-free core. The Qt-facing `ModelImportService` (`viewport/modelimportservice.{h,cpp}`) owns the orchestration: it looks up the importer (`ImporterRegistry::forPath`), runs `load()`, `QImage`-decodes each mesh's `TextureSource` (from its path *or* its embedded bytes) into tightly-packed RGBA8 (`MeshData::diffusePixels`), and calls `VulkanRenderer::addModel(ModelData)` — keeping the renderer free of any image-codec dependency while supporting every format Qt's image plugins do. The full chain is `MenuManager` (File → Import → `.OBJ`, a `QFileDialog`) → `ViewportWidget::importObj` → `VulkanWindow::importObj` (queues the path if the renderer isn't built yet — it's created lazily on first expose) → `ModelImportService::importInto` → `MeshImporter::load` → `VulkanRenderer::addModel` → `Scene::addModel`. `main.cpp` also feeds any `.obj` on the command line through `ViewportWidget::importObj` (drag-onto-exe / "open with"), which is why the queue-until-ready step matters. Imports run on the GUI thread between frames; the batched upload blocks briefly on its single submit but touches no in-flight state, so the next recorded frame just picks the new model up. Because that work is synchronous and can still be slow (large meshes, many textures), `ModelImportService` drives a modal staged `QProgressDialog` (read → per-mesh texture decode → GPU upload) — a `showProgress` flag gates it: interactive imports pass `true`, but the startup/command-line drain (called from inside `initializeVulkan()`/`exposeEvent()`) passes `false`, because a modal dialog's `processEvents()` could re-enter the expose/init path. The progress UI lives only in this Qt layer; the importers and renderer core stay Qt-free. **The File → Import menu is deliberately *not* registry-driven** — it lists all 10 formats as hardcoded entries in `menumanager.cpp` (alphabetical), with `.OBJ` (→ `importObjFile`) and **`.DUF (DUF File)`** (→ `importFigureFile`, the character-figure entry) wired and the rest disabled placeholders, so enabling a newly-added importer means flipping its menu entry from disabled to a real `QFileDialog`+import connect there. **Not yet:** non-diffuse PBR maps (normal/metal/rough — OBJ doesn't natively carry them), and the other 8 mesh Import formats are still disabled placeholders.

**Native figure importer** (`import/figure/`): imports rigged, morphable character figures from their **native scene format** — a gzip-compressed-JSON preset (`.duf`) that references geometry/rig/skin/morph/UV data files (`.dsf`) across a content folder. This is a much bigger importer than a mesh format (a figure is geometry + material zones + skeleton + skin weights + morphs), so it does **not** use the static `MeshImporter`/`ImporterRegistry` path (which returns `ModelData` and needs no external context) — it has its own rich IR (`FigureData`/`FigureMesh`/`FigureMaterial` in `figuredata.h`) and its own loader that needs the content-root folders to resolve cross-file URIs. **Legal/naming:** per the standing no-brand rule, no product or figure-line names appear anywhere in this code — and they don't need to: the format is self-describing, so **one figure-agnostic reader handles every figure family** (geometry, bones, weights, morphs, materials all come out of the files) — verified importing and rendering all seven target figure families (male & female base figures across several generations, plus a unified newer figure), including textured, morphed character presets. Qt-free layers, bottom-up:
- `figuredocument.{h,cpp}` — loads one file: read → gzip-sniff (`1f 8b`) → inflate (miniz) → parse (nlohmann). The single miniz-consuming TU.
- `uriresolver.{h,cpp}` — resolves the URL-encoded, root-relative cross-file URIs (`/data/…#id`, `/Runtime/…`) against the content roots (first existing wins; case tolerated by NTFS — a case-fold pass is the cross-platform TODO), and **caches** parsed docs so a shared base file isn't re-inflated per reference.
- `geometryparser` / `uvparser` / `materialparser` — parse the base `.dsf` geometry (quads→tris, grouped by material zone), the external UV set (with per-corner **seam overrides**, so the mesh splits at UV seams; whole-surface smooth normals keep zone boundaries seamless), and the preset's physically-based materials (base color + texture maps — referenced either as a direct `image_file` path or, in newer generations, an `image` index into `image_library`; normal/bump + roughness captured for later PBR). Transparency for the eye's clear shells is keyed on a strong **Refraction Weight** (not a "no-map + low-roughness" heuristic, which wrongly turned some figures' untextured skin invisible).
- `nodeparser` / `skinparser` — the skeleton (bone hierarchy + rest transforms from `node_library`) and the per-vertex top-4 skin weights (from the `SkinBinding` modifier), for GPU skinning.
- `morphresolver` / `morphparser` — the character's shape: `morphresolver` evaluates the preset's dialed channels through their **channel-driver formulas** (control → driven morphs); `morphparser` reads each reached morph's sparse deltas, baked into the base vertices at import.
- `correctiveparser.{h,cpp}` — detects + parses a **pose corrective** (joint-driven corrective morph) from a modifier: confirms it's rotation-driven, translates its `push`/`mult`/`spline_tcb` formula into the engine's stack-program IR (`PoseCorrective` in `modeldata.h`), and folds its character/enable gates to constants (dropping any a gate switched off). See the correctives paragraph below.
- `subdivision.{h,cpp}` — **Catmull-Clark** subdivision of the base cage into a smoother render mesh (positions smooth; UVs per-corner + skin weights refined linearly), then assembled per zone like the un-subdivided path. Also exposes `subdivideDeltaField` to carry a corrective's sparse deltas onto the subdivided cage (Catmull-Clark being linear). See the subdivision paragraph below.
- `figureimporter.{h,cpp}` — orchestrates: preset `.duf` → find the figure node's `geometries[0].url` → resolve+load the base `.dsf` → parse geometry → **bake dialed morphs** → parse skeleton + skin weights → **discover pose correctives** → resolve+parse the UV set → **subdivide the cage** (and each corrective's deltas) → assemble per-zone meshes (with joint weights) → attach each zone's resolved material → `FigureData` (meshes + skeleton + weights + correctives).

The Qt-facing `FigureImportService` (`viewport/figureimportservice.{h,cpp}`, the figure analogue of `ModelImportService`) resolves the **content-root folder(s)** the preset's `/data/…#id` URIs resolve against — **auto-detected** by walking up from the imported file to the ancestor containing `data/`, **unioned with any user-configured roots** (`Constants::PREF_FIGURE_CONTENT_ROOTS`, a newline-separated path list in Preferences), auto-detected first (most authoritative for a self-contained library) then configured. This matters because content is commonly split: a figure browsed from a **presets-only folder** (`.duf`s with no co-located `data/`) has *no* auto-detectable root, so without the configured fallback its geometry/morphs/skin/UVs (all under `data/`) can't be found and **every** figure fails with "cannot resolve base geometry" — the configured roots are what make that case work. It then runs `FigureImporter`, converts `FigureData`→`ModelData` applying the **cm→world unit scale (÷100)** so a ~180 cm figure lands at grid scale, decodes textures via the shared `ModelImportService::decodeMeshTexture`, and uploads through the **existing lit mesh pipeline** (`addModel`). Routing mirrors OBJ: `ViewportWidget::importFigure` → `VulkanWindow::importFigure` (queues until the renderer exists) → the service; File → Import → **`.DUF (DUF File)`** (the character-figure entry in the alphabetical format list, `*.duf`/`*.dsf` filter), command-line/"open-with" `.duf`/`.dsf`, and **double-clicking a figure asset in the Asset Manager grid** (`AssetManagerWidget::importFigureRequested` → `ViewportWidget::importFigure`, the figure analogue of the `.obj` → `importModelRequested` route) all route here. **Failure feedback (interactive path only, `showProgress`):** `importInto` classifies the failure and responds in kind. A `.duf` that isn't a figure (pose/material/light presets share the extension and all appear in the grid) throws "no geometry reference found" → a `QMessageBox` ("this may be a pose/material preset rather than a figure…"). A real figure whose `data/` library isn't on any known root (empty roots, or a resolve error) is the **recoverable** case: a **"Locate Content Folder…"** prompt → a folder picker → the chosen root is persisted to `PREF_FIGURE_CONTENT_ROOTS` and the import is **retried once** with it folded in (a single-shot `for (attempt < 2)` loop), so the fix is one-time and remembered. The startup/command-line drain (`showProgress=false`) stays dialog-free (returns false silently) to avoid re-entering the expose path. The actual per-attempt work lives in a file-local `runFigureImport()` that `importInto` calls inside that loop. Materials also **merge the `material_library` base** each scene material extends by `url` (`#id`): a scene material only *overrides* channels, so roughness and the transparency-defining channels (which live on the base) are read from the merge — essential for the eye's clear shells. **Current state:** a figure renders textured in bind pose with per-zone roughness-driven specular, cheap **subsurface skin shading** (wrap-lighting + a warm subsurface band, in `mesh.frag`), alpha-blended transparency for the eye's clear shells (cornea/moisture — detected via the material's `Refraction Weight` channel read from the merged base, so the iris shows through), tangent-space **normal-map** support (screen-space cotangent frame — no vertex tangents), and grayscale **bump** maps applied as a mip-stable **texture-space central-difference** perturbation (height sampled at `textureSize`-derived texel offsets — this replaced an earlier screen-space version that was too noisy on the UDIM maps), which is what gives the base skin its surface grain. **Phase 3 (skeleton + skinning) is done and the figure is posable:** `nodeparser` builds the bone hierarchy from `node_library`, `skinparser` inverts the `SkinBinding` modifier into per-base-vertex top-4 weights, `assembleFigureMeshes` attaches those to each render vertex, and `FigureImportService` hands the renderer a `ModelData` with a skeleton (`ModelBone` list). At the GPU layer every `Model` carries a joint-matrix storage buffer (see the mesh-pipeline notes) and a runtime skeleton; `Model::setBoneRotation(name, eulerDegrees)` poses a joint and recomputes the skin matrices. **Phase 2 (character-identity morphs) is done:** `morphresolver` walks the preset's dialed channels through their **channel-driver formulas** — a character dials a *control* (e.g. `CTRL<character> = 1`) whose linear `push`/`mult` formulas drive the real head/body shape morphs (`FHM…`/`FBM…`) — and `morphparser` reads each reached morph's sparse deltas, which the importer **bakes into the base vertices** (`position += weight·delta`) before assembly, so the generic base becomes the specific character (verified on real character presets: face + body shape). **Joint-center adjustment is part of this:** the same full-body/head morph modifiers also carry driver formulas whose *output* is a bone's `center_point/{x,y,z}` (a `FBM<character>` typically has hundreds — e.g. `hip.center_point.y += FBM<character>.value · coeff`), so the rig follows the character's new proportions. `morphresolver` returns these as a per-bone `JointCenterOffsets` map (routed out of the same formula walk that resolves morph weights — a bone `center_point` is *not* a morph channel to propagate), and `figureimporter` adds each offset to the matching `FigureBone::origin` right after `parseSkeleton` — before skin-weight parse, corrective discovery, subdivision, and assembly — in the same native-cm space as `origin` (the cm→world × `figureScale` in `toModelData` then scales mesh and skeleton together). Without this, a *base-figure* rig sits inside a *morphed* mesh: posed limbs pivot at the wrong places and the joint overlay floats off the body. `end_point`/`orientation` outputs are skipped — the bind is translation-only and orientation is read straight from the node, so they don't affect skinning. Verified: an unmorphed base figure shifts 0 bones; a strongly-stylized character shifts ~169/171 (max ~6.4 cm). **Posing is anatomically correct:** a bone's rest transform stays translation-only (the orientation cancels at rest — `T·OR·OR⁻¹`), and `setBoneRotation` applies the rotation in the joint's oriented frame (`localBind · OR · R(euler, rotation_order) · OR⁻¹`), so an elbow/knee/shoulder bends about its true axes (verified). **Joint rotation limits are enforced:** each bone's `rotation/{x,y,z}` channel carries a `min`/`max` range (degrees) and a `clamped` flag (the format's per-channel "use limits") — the joint's anatomical range of motion (a knee ≈ x∈[-11°,155°], the neck ≈ x∈[-30°,25°]). `nodeparser` reads these into `FigureBone` (matching axis by channel *id*, not array position, since the array is ordered per `rotation_order`), they flow through `ModelBone`→`GpuBone`, and `Model::clampBoneEuler()` — called at the top of `applyBoneEuler()` and in the `applyPose()` loop, the two points every posing path (free-drag, gizmo, pose load, undo) funnels through — clamps each *limited* axis to `[min,max]` in place (so accumulated drags stop cleanly at the limit and saved/queried poses reflect the clamped angle). Only axes flagged `clamped` are constrained; free axes (twist bones) and models without a skeleton (OBJ) default to unconstrained, so nothing else is affected. Verified: a base figure reports 399 limited axes across 171 bones, and a 300° request on the knee clamps to 155°, on the neck to 25°. **Not yet:** limits aren't surfaced in the UI (no visual range indicator on the gizmo), and there's no global "use limits off" override; morph-driven limit *adjustments* (a formula driving `rotation/x?min`) aren't applied — the base node limits are used as-is. **Interactive posing UI:** the **skeleton overlay is hidden by default** — the rotate gizmo (below) is the sole visual affordance, so the character isn't cluttered with a bone cage. `Scene::record` still owns a coloured line list drawn through a dedicated line pipeline (over the mesh, depth test off), but only emits the joint→parent segments when `m_showSkeleton` is on (the flag/`setShowSkeleton` plumbing survives for a future View toggle; nothing sets it true now); the gizmo rings are emitted **independently of that flag**, whenever a joint is selected. Crucially, **picking is independent of what's drawn** — `Scene::selectBoneAt` projects every bone to screen and hit-tests within a pixel radius regardless of overlay visibility — so joints stay clickable even though invisible. In `VulkanWindow`, a **left press that lands on a joint** (nearest projected bone within a pixel radius — `Scene::selectBoneAt`) selects it and enters posing, bringing up the gizmo, so that drag **rotates the joint** (`Scene::nudgeSelectedBone` → `Model::setBoneRotation` in the oriented frame) instead of orbiting the camera; a left press on empty space orbits (even while a joint stays selected — `selectBoneAt` returns -1 on a miss but keeps the selection). `setBoneRotation(name, eulerDegrees)` remains the underlying primitive. A **rotate gizmo** draws three axis rings around the selected joint (X/Y/Z = red/green/blue) in the joint's own rotation frame (`Model::selectedBoneFrame` = `parentGlobal·localBind·orient`, so each ring maps to one Euler channel — including twist, which free-drag couldn't reach): a left-press that grabs a ring (`Scene::gizmoAxisAt`) enters an **axis-constrained** rotate where the drag's swept screen-angle about the joint drives that one channel (`Scene::rotateGizmo`), while a press on the joint itself still free-rotates. **Pose undo/redo** (`Ctrl+Z`/`Ctrl+Y`, handled in `VulkanWindow::keyPressEvent`) snapshots the pre-edit pose on each committed drag (via `Scene::capturePose`/`applyPose`, the same primitives as pose save/load) onto an undo stack; applying an undo re-runs correctives like any pose change. **Driven figure scale is applied:** `morphresolver` accumulates the preset's `scale/general` driver-formula contributions into `FigureData::figureScale`, which `FigureImportService` folds into the cm→world scale (so a taller/shorter character lands at the right height, mesh and skeleton together). **Pose save/load is wired:** `Model::capturePose()`/`applyPose()` (bind pose + named Euler rotations) round-trip through `Scene::savePose/loadPose` (a plain-text `.pose` file, one `name rx ry rz` line per posed joint — safe because figure bone names are space-free tokens), forwarded out through `VulkanRenderer`→`VulkanWindow`→`ViewportWidget`; File → **Save Pose… / Load Pose…** drive it, and a `.pose` path on the command line / "open-with" applies onto the imported figure (queued behind it like the figure itself). **Pose correctives are done:** joint-driven corrective morphs that fire as a function of bend angle to fix the mesh crumpling ("candy-wrapper") at deep elbow/knee/shoulder/hip bends. They aren't listed by the preset, so `figureimporter` discovers them **structurally** — a morph whose driver formula is driven by a joint `rotation/{x,y,z}` channel — scanning the corrective/flexion folders (plus each dialed character's own morph folder) under `<figure>/Morphs`; this is figure-generation-agnostic (the corrective files are named differently from one generation to the next, but the structure is identical — detection is never keyed on file/brand names). `correctiveparser` translates each driver formula (the `push`/`mult`/`spline_tcb` vocabulary the base correctives actually use) into a small stack-program IR (`CorrectiveOp`/`CorrectiveFormula`/`PoseCorrective` in `modeldata.h`), **folding the character/enable gates (the mult-stage drivers) to constants at import** — resolved to the dialed weight if the preset dials that channel, else the channel's own default `value` — so a non-loaded character's correctives (gate → 0) are dropped at import while a figure's default-on "base joint correctives" master toggle (default 1) keeps the base set live. At the engine, each `Model` keeps the affected meshes' base (uncorrected) vertices and, per corrective, the render vertices its base-vertex deltas map onto (built once from each mesh's `baseVertex` array); `refreshCorrectives()` re-evaluates every corrective's weight from the current pose (a Catmull-Rom spline through the driver knots, clamped per-segment to avoid overshoot × the folded gate) and, if any changed, re-morphs the affected meshes on the CPU (base + Σ weight·delta) and re-uploads them (a `vkDeviceWaitIdle` first, since an in-flight frame may reference the old buffers) — the GPU skinning then bends the *corrected* bind mesh. It runs immediately on `setBoneRotation`/`applyPose` and on interactive **drag release** (`Scene::finalizePose`, deferred during the drag since re-uploading geometry mid-drag would stutter). Verified end-to-end on two figure families (113 and 97 correctives discovered): deeply-bent elbows/knees fire the right correctives (22 / 8 active respectively) and deform cleanly. **Catmull-Clark subdivision is done** (`import/figure/subdivision.{h,cpp}`, wired in `figureimporter` at `kSubdivisionLevels = 1`): the low-res base cage is smoothed into the render mesh so limbs/torso/face read round rather than faceted. Positions follow the smooth Catmull-Clark rules on the watertight cage (face/edge/vertex points; boundary edges use the cubic B-spline rule); UVs are kept **per polygon corner** and refined *linearly* (each sub-face's corners get their parent face's corner UVs averaged), so texture seams split exactly as before; skin weights are refined by blending (edge/face points average their contributors' top-4, vertex points keep theirs). The subdivided cage is then run through the *same* de-index/seam-split/smooth-normal assembly as the base path, so `Scene`/`Model`/skinning/correctives are all unchanged — they just see ~3–4× the vertices (a ~16.5k base cage → ~56k affected render verts at level 1). **The corrective machinery needed no change** because Catmull-Clark is a *linear* operator: each corrective's sparse base-cage delta field is carried onto the subdivided cage by the same stencils (`subdivideDeltaField`) at import, so the runtime re-morph (`base + Σ weight·delta`) works directly on the dense mesh. Verified: the subdivided figure renders smoother, textures + skinning intact, and the base correctives still fire (22/113 active on a bent-elbow/knee pose, re-morphing the dense zones). Cost: ~+2.5 s import (subdivision + subdividing the delta fields) and a heavier re-upload on pose-settle. **Not yet:** the *identity*-morph driver-formula evaluator (`morphresolver`) still approximates spline/other ops as no-ops (the corrective path has its own real spline evaluator); the gizmo's axis-drag isn't gimbal-exact (it drives one Euler channel) and its undo is keyboard-only (the Edit menu's Undo/Redo entries are still disabled placeholders); grafted attachment meshes (separate fitted meshes — e.g. anatomy or clothing) aren't merged. The core figure pipeline — import, character morphs, materials, rig, skinning, correctives, subdivision, and the posing UI — is complete.

The `Camera` (`scene/camera.{h,cpp}`) is a pure-GLM orbit camera; its projection negates `[1][1]` for Vulkan's flipped clip-space Y on top of the project-wide `GLM_FORCE_DEPTH_ZERO_TO_ONE`. Natural next increments: more importers (glTF/USD) — each a new `MeshImporter` under `import/<fmt>/` plus one `ImporterRegistry` line — and richer materials (PBR map slots beyond the diffuse texture — normal/metal/rough — which need a richer source format than OBJ). Each slots into the existing `import/` registry, `Scene`/`Mesh`, and `VulkanTexture` modules without disturbing the others.
